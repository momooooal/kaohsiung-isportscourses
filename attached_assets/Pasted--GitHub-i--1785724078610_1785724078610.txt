我想規劃一個放在 GitHub 上的「高雄市運動i臺灣常態課程查詢網站」。請先完整閱讀以下需求，整理你對專案的理解、資料關聯、功能架構與可行性，暫時不要開始撰寫網站程式。

## 一、網站核心目標

目前 i運動資訊平台將相關資訊分散在「運動課程」與「常態性課程」兩個區域。

民眾若想確認某一門常態課程是否屬於「運動i臺灣計畫」，必須：

1. 先到「運動課程」查詢。
2. 確認該活動的「活動來源」是否為「運動i臺灣計畫」。
3. 記住活動或課程名稱。
4. 再前往「常態性課程」重新查詢。
5. 找到詳細課程資料及報名頁面。

這個流程非常不直覺，也容易找不到正確課程。

我希望建立一個新網站，自動整合這兩個區域的資料，讓民眾進入網站後，就能直接查詢：

* 辦理縣市為「高雄市」
* 活動來源為「運動i臺灣計畫」
* 屬於「常態性課程」的實際課程資訊

民眾不需要再自行前往兩個不同頁面交叉比對。

## 二、資料來源

主要資料來源為 i運動資訊平台。

常態性課程網址：

https://isports.sa.gov.tw/Apps/TIS/PFM05/PFM0560M_01V1.aspx?MENU_PRG_CD=1&ITEM_PRG_CD=6

上述網址只是第一頁，實際上還有多個分頁。網站必須能取得所有分頁，而不是只讀取第一頁。

另外，還需要取得 i運動資訊平台「運動課程」中的資料，用來確認：

* 辦理縣市
* 活動來源
* 課程辦理情形
* 活動名稱
* 主辦單位
* 活動內容
* 其他可用於對照常態性課程的欄位

請先確認 i運動資訊平台是否有可使用的 API、公開資料或其他穩定的資料取得方式。若沒有完整 API，再評估是否需要從網頁取得資料。

## 三、資料篩選條件

新網站前台只顯示同時符合以下條件的課程：

1. 課程辦理縣市為「高雄市」。
2. 活動來源為「運動i臺灣計畫」。
3. 屬於「常態性課程」。
4. 能夠與「運動課程」中的活動資料正確對應。

以下資料不要顯示：

* 其他縣市的課程
* 活動來源為「平台登錄」的課程
* 活動來源為「全國性運動團體計畫」的課程
* 無法確認是否屬於運動i臺灣計畫的資料
* 明顯重複或對應錯誤的資料

### 第一層：運動課程或計畫資料

## 五、網站主要功能

### 1. 課程辦理情形分類

網站應以「運動課程」中的「課程辦理情形」作為主要分類。

可能包含：

* 全部課程
* 招生中
* 即將開始
* 辦理中
* 已額滿
* 候補中
* 已結束
* 暫停
* 取消

實際分類名稱應以來源平台提供的狀態為準。

如果來源平台沒有提供完整狀態，可以根據報名期間及課程期間輔助推算：

* 尚未到報名開始日期：即將開放
* 位於報名期間內：報名中
* 報名已截止，但課程尚未開始：即將開課
* 課程已開始但尚未結束：辦理中
* 課程結束日期已過：已結束

但「已額滿、候補中、暫停、取消」等狀態不可只依日期推算，必須以來源資料為準。

### 2. 行政區篩選

網站只顯示高雄市，因此不需要再讓民眾選擇縣市。

請改為提供「高雄市行政區」篩選，例如：

* 左營區
* 鼓山區
* 三民區
* 苓雅區
* 前鎮區
* 鳳山區
* 楠梓區
* 岡山區
* 其他高雄市行政區

行政區可從課程地址中自動擷取，但若無法判斷，應標記為「行政區待確認」。

### 3. 其他篩選功能

* 運動項目

* 課程辦理情形
* 上課時段
* 報名期間
* 課程期間

### 4. 關鍵字搜尋

搜尋範圍至少包含：

## 八、報名方式

新網站主要負責資料整合、搜尋及導引，不自行建立報名系統。

民眾點擊「前往報名」後，應導向 i運動資訊平台的官方報名頁面。

網站不要自行收集：

* 姓名
* 電話
* 身分證字號
* 生日
* 報名名單
* 其他個人資料

避免發生個資保存、名額不同步及報名結果不一致的問題。

## 九、自動同步需求

我希望 i運動資訊平台資料更新後，新網站也能定期自動更新。

網站預計使用：

* GitHub Repository
* GitHub Pages
* GitHub Actions

預計運作方式：

1. GitHub Actions 定時執行資料更新程式。
2. 讀取 i運動資訊平台所有相關分頁或 API。
3. 取得「運動課程」及「常態性課程」資料。
4. 篩選高雄市。
5. 篩選活動來源為運動i臺灣計畫。
6. 配對活動與實際常態課程。
7. 移除重複資料。
8. 產生前端使用的 JSON 資料檔。
9. 自動更新 GitHub Repository。
10. 重新發布 GitHub Pages。

同步頻率可以先規劃為：

* 每天上午同步一次
* 每天下午同步一次
* 保留管理者手動執行同步的功能

請將此功能描述為「定時同步」，不要宣稱是完全即時同步。

## 十、同步失敗處理

網站需要有基本的容錯機制：

* 同步失敗時，不可把原有資料清空。
* 保留最近一次成功同步的資料。
* 記錄同步成功或失敗時間。
* 記錄錯誤原因。
* 若部分頁面讀取失敗，應保留其他成功取得的資料。
* 不可因單筆課程錯誤而讓整批同步停止。
* 應能列出無法配對、解析失敗或欄位異常的課程。
* 前台顯示「資料最後更新時間」。
* 必要時顯示「目前顯示最近一次成功同步資料」。

## 十一、資料正確性原則

1. 不可自行修改官方課程內容。
2. 不可把推測資料當成官方資料。
3. 自動推算的狀態應明確標示為系統判斷。
4. 官方資料與系統推算衝突時，以官方資料為準。
5. 每門課程應保留原始資料網址。
6. 應避免同一門課程因不同頁面或不同抓取時間而重複顯示。
7. 若資料配對信心不足，應列入待確認資料，不直接顯示為已確認課程。

## 十二、資料來源與免責說明

網站頁尾需要固定顯示類似以下內容：

「資料來源：運動部全民運動署 i運動資訊平台。本網站提供高雄市運動i臺灣計畫課程之整合查詢服務，實際課程內容、名額、辦理情形及報名資訊，仍以 i運動資訊平台及主辦單位最新公告為準。」

同時請評估使用及呈現官方資料時，是否需要遵守其他政府資料開放、著作權、網站使用條款或流量限制。

## 十三、網站定位

這個網站不是單純複製 i運動資訊平台的常態性課程頁面。

真正的核心價值是：

「先利用運動課程資料確認活動是否為高雄市的運動i臺灣計畫，再將符合條件的常態性課程整合成一個方便搜尋、分類及前往官方報名的高雄專屬查詢網站。」
